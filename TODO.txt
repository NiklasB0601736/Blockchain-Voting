TODO - Zielarchitektur: verteiltes Zero-Trust Voting
====================================================

Projektziel
-----------

[ ] Die Wahlkette soll nicht lokal auf einem Rechner liegen, sondern von n
    beliebig vielen Nodes repliziert und verifiziert werden.

[ ] Auf der Chain duerfen keine Namen und keine Klarstimmen gespeichert werden.

[ ] Stimmen sollen verschluesselt auf der Chain stehen und oeffentlich
    einsehbar sein.

[ ] Jeder Node soll spaeter pruefen koennen, ob das veroeffentlichte Ergebnis
    korrekt aus den gespeicherten verschluesselten Stimmen berechnet wurde.


Phase 1 - Homomorphe Verschluesselung als Prototyp
--------------------------------------------------

[x] Ein kleines Kryptografie-Modul bauen, z.B. `crypto_tally.py`.

[ ] Zuerst eine Ja/Nein-Wahl als Demo implementieren:
    - Nein = 0
    - Ja = 1
    - Stimme wird als Enc(0) oder Enc(1) gespeichert.

[ ] Probabilistische Verschluesselung verwenden:
    - gleiche Klarstimme darf nicht immer gleich aussehen
    - Enc(1) muss bei jeder Abgabe anders aussehen koennen
    - die Zufallswerte/Nonces duerfen nicht auf der Chain stehen.

[x] Exponential-ElGamal-Prototyp fuer Level 3 bauen:
    - verschluesselte One-Hot-Kandidatenstimmen
    - homomorphe Aggregation
    - Entschluesselungsbeweis per Chaum-Pedersen-Proof
    - oeffentliche Pruefung, dass das Ergebnis zum encrypted tally passt.

[x] Homomorphe Aggregation zeigen:
    - Enc(v1) + Enc(v2) + ... = Enc(total)
    - je nach Verfahren kann die Operation intern Multiplikation sein.

[x] Nur das Gesamtergebnis entschluesseln, niemals einzelne Stimmen.

[x] Tests schreiben:
    - gleiche Stimme erzeugt unterschiedliche Ciphertexts
    - verschluesselte Stimmen lassen sich korrekt aggregieren
    - entschluesselte Summe stimmt mit den Teststimmen ueberein


Phase 2 - Chain-Speicher fuer verschluesselte Ballots
-----------------------------------------------------

[ ] Vote-Datenmodell umbauen:
    - keine `vote_option` als Klartext auf der Chain speichern
    - stattdessen `encrypted_vote` oder `encrypted_ballot` speichern.

[ ] Fuer mehrere Optionen spaeter einen Vektor speichern:
    - Option A: [Enc(1), Enc(0), Enc(0)]
    - Option B: [Enc(0), Enc(1), Enc(0)]
    - Option C: [Enc(0), Enc(0), Enc(1)]

[ ] Ergebnislogik umbauen:
    - nicht lokale Klarstimmen zaehlen
    - alle Ciphertexts homomorph aggregieren
    - verschluesselte Gesamtsumme speichern/veroeffentlichen.

[ ] Oeffentliche API ergaenzen:
    - alle verschluesselten Ballots abrufen
    - verschluesselte Gesamtsumme abrufen
    - veroeffentlichtes Ergebnis abrufen
    - Verifikationsstatus abrufen.


Phase 3 - Gueltigkeitsbeweise fuer Stimmen
------------------------------------------

[ ] Klaeren, welches ZK-Proof-Verfahren genutzt werden soll.

[ ] Fuer Ja/Nein-Wahl beweisen:
    - verschluesselte Stimme ist entweder 0 oder 1.

[ ] Fuer Mehrfachoptionen beweisen:
    - genau eine Option ist 1
    - alle anderen Optionen sind 0.

[ ] Chain/Nodes muessen ungueltige Ballots ablehnen.

[ ] Tests schreiben:
    - Enc(0) wird akzeptiert
    - Enc(1) wird akzeptiert
    - Enc(2), Enc(999) oder mehrere gesetzte Optionen werden abgelehnt.


Phase 4 - Anonyme Wahlberechtigung und Double Voting
----------------------------------------------------

[ ] Namen duerfen nicht auf der Chain gespeichert werden.

[ ] Wahlberechtigung anonym beweisen:
    - z.B. ueber Semaphore oder ein vergleichbares ZK-Membership-System.

[ ] Double Voting ueber `nullifier_hash` verhindern:
    - pro Wahl ist jeder Nullifier nur einmal erlaubt
    - Nullifier darf nicht direkt auf die Person zurueckfuehren.

[ ] Aktuelle lokale Commitment-Loesung spaeter ersetzen:
    - aktuell verhindert `voted_commitments` doppelte Stimmen in der Demo
    - Ziel ist ein anonymer Nullifier statt Commitment als Identifikator.


Phase 5 - Wahlkomitee und Threshold Decryption
----------------------------------------------

[x] Privaten Entschluesselungsschluessel nicht bei einer einzelnen Person
    speichern.

[x] Threshold-Verfahren planen:
    - z.B. 3 von 5 Komitee-Mitgliedern muessen zustimmen
    - einzelne Key Shares reichen nicht zum Entschluesseln.

[x] Komitee entschluesselt nur die homomorph aggregierte Gesamtsumme.

[x] Komitee veroeffentlicht:
    - Ergebnis
    - Partial Decryptions
    - kryptografische Beweise, dass die Partial Decryptions korrekt sind.

[x] Ersten Single-Key-Prototyp fuer Decryption Proofs bauen:
    - spaeter durch Threshold-Prototyp erweitert.

[x] Jeder Node kann pruefen:
    - Partial Decryptions sind gueltig
    - Ergebnis passt zur verschluesselten Gesamtsumme.


Phase 6 - Oeffentliche Verifikation
-----------------------------------

[ ] Jeder Node soll lokal nachvollziehen koennen:
    - alle Ballots sind gueltig
    - kein Nullifier kommt doppelt vor
    - alle gueltigen Ballots sind in die Summe eingegangen
    - die veroeffentlichte verschluesselte Summe ist korrekt
    - das entschluesselte Ergebnis passt zur verschluesselten Summe.

[ ] Verifikationsfunktion/API bauen:
    - `GET /api/verify/{election_id}` soll diese Checks spaeter abbilden.

[ ] Ergebnis darf nur als gueltig gelten, wenn alle Checks bestanden sind.
